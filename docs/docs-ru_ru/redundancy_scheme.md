# Схема резервирования UPF в двух конвергентных pLTE/p5G ядрах

Документ описывает два варианта резервирования пользовательской плоскости (UPF)
для связки из **двух конвергентных ядер** (EPC + 5GC в каждом), подключённых к
одной базовой станции gNB. Варианты различаются способом маршрутизации downlink
и сохранением IP-адреса абонента при отказе ядра.

- **Вариант A — разделённые пулы (prefix-routing).** Непересекающиеся пулы
  IP-адресов абонентов, маршрутизация в DN по префиксу. Не требует изменений в
  работе системы. Два ядра сети работают полностью независимо.
- **Вариант B — общий пул IP-адресов (ECMP + IPIP miss-forward).** Общий пул
  адресов, ECMP в DN на оба ядра, пересылка «чужого» downlink между ядрами через
  IPIP. Статически назначаемые IP-адреса при отказе ядра сохраняются, т.к.
  выведены в общий пул.

Оба варианта работают в режиме **Active-Active** (оба ядра одновременно
обслуживают своих абонентов) и **не** обеспечивают бесшовного переключения
сессий: при отказе якорного ядра абонент выполняет повторную регистрацию
(re-attach) в резервном ядре.

---

## 1. Назначение и область применения

Цель схемы — повысить доступность сервиса передачи данных пользовательского
трафика, когда одна gNB или набор gNB одновременно обслуживаются двумя
независимыми конвергентными ядрами.

Схема обеспечивает:

- **Резервирование маршрута downlink** (направление к UE): при отказе одного ядра
  абоненты восстанавливают обслуживание через резервное ядро.
- **Горячий резерв ядра**: второе ядро постоянно активно и готово принять
  абонентов отказавшего.

**Важно:** переключение **не бесшовное**. Состояние PDU-сессии (PDR/FAR/QER,
N3 TEID, NAS-контекст) существует только в ядре-якоре. При отказе якоря абонент
выполняет повторную регистрацию в живом ядре: повторная аутентификация
(5G AKA / EAP-AKA'), новая PDU-сессия, возможна смена IP. RTO — секунды. Это
осознанное ограничение схемы; репликация состояния сессий между ядрами не
предусмотрена (не стандартизована в 3GPP).

## 2. Термины и сокращения

| Термин | Определение |
|---|---|
| **Конвергентное ядро** | ядро, объединяющее функции EPC (LTE) и 5GC (5G); gNB подключается по NG к 5GC-стороне. |
| **DN** | Data Network — внешняя сеть данных (N6 / SGi). |
| **gNB** | базовая станция NR, подключённая по NG к 5GC-стороне каждого ядра. |
| **PDR / FAR / QER** | Packet Detection Rule / Forwarding Action Rule / QoS Enforcement Rule — элементы состояния сессии. |
| **N3** | интерфейс RAN↔UPF (GTP-U). |
| **N6** | интерфейс UPF↔DN (IP). |
| **N3 TEID** | идентификатор туннеля GTP-U, назначаемый SMF для PDU-сессии. |
| **IPIP** | инкапсуляция IPv4-в-IPv4 (IP-in-IP, протокол 4) или IPv6-в-IPv4. |
| **Miss-правило (catch-all)** | правило «по умолчанию»: при отсутствии сессии по DST IP пакет пересылается пиру (Вариант B). |
| **Якорное ядро** | ядро, в котором фактически создана PDU-сессия абонента (хранит PDR/TEID). |
| **Prefix-routing** | маршрутизация downlink по префиксу пула абонентских IP (Вариант A). |

## 3. Архитектура и топология

Общая топология для обоих вариантов. Различие — в поведении DN и наличии
IPIP-связи (только Вариант B).

```
                      ┌─────────────────────────────────────────────┐
                      │              Data Network (DN)               │
                      │  A: prefix-routing по пулу   B: ECMP per-flow │
                      └────────────────┬──────────────┬──────────────┘
                                       │              │
                              [маршрут к UPF-A]  [маршрут к UPF-B]
                                       │              │
          ┌────────────────────────────▼──┐      ┌────▼────────────────────────┐
          │     Ядро А (конвергентное)    │      │     Ядро Б (конвергентное)   │
          │  ┌──────────────────────────┐ │      │  ┌─────────────────────────┐│
          │  │ AMF/SMF (EPC+5GC)        │ │      │  │ AMF/SMF (EPC+5GC)       ││
          │  └────────────┬─────────────┘ │      │  └────────────┬────────────┘│
          │               │ PFCP (N4)     │      │               │ PFCP (N4)    │
          │  ┌────────────▼─────────────┐ │      │  ┌────────────▼────────────┐│
          │  │       UPF-A (XDP)        │◄┼──────┼─►│       UPF-B (XDP)       ││
          │  └────────────┬─────────────┘ │      │  └────────────┬────────────┘│
          └───────────────┼───────────────┘      └───────────────┼────────────┘
                         │ N3 (GTP-U)                    N3 (GTP-U)│
                         │           IPIP-связь                   │
                         │       (только Вариант B,               │
                         │        2+ линка, ECMP)                 │
                    ┌────▼────────────────────────────────────────▼────┐
                    │                       gNB                         │
                    │         NG → 5GC ядра А,  NG → 5GC ядра Б         │
                    └──────────────────────────────────────────────────┘
```

Ключевые элементы:

1. **gNB подключена к обоим ядрам** по NG (к 5GC-стороне каждого конвергентного
   ядра). gNB знает, в каком ядре создана каждая PDU-сессия (по назначенному
   N3 TEID), поэтому **uplink всегда уходит в якорное ядро** — пересылка uplink
   между ядрами не требуется в обоих вариантах.
2. **DN → UPF:**
   - Вариант A: маршрутизация по префиксу (пул A → UPF-A, пул B → UPF-B).
   - Вариант B: ECMP на оба UPF, хеширование строго **per-flow (5-tuple)**.
3. **IPIP-связь UPF-A ↔ UPF-B** — только Вариант B. Рекомендуются **2+
   независимых линка (ECMP/LACP)**; при одном линке — единая точка отказа (SPOF).

## 4. Два варианта схемы

### 4.1. Сводное сравнение

| Свойство | Вариант A — разделённые пулы | Вариант B — общий пул |
|---|---|---|
| Маршрутизация DL в DN | по префиксу пула | ECMP per-flow |
| Дополнительный межядерный DL-трафик | **Отсутствует** (IPIP не нужен) | ~50% (постоянно) |
| Поддержка в UPF | **не требуется** | требуется (miss→IPIP, decap, anti-loop) |
| IPIP-связь | не используется | требуется (2+ линка) |
| Статический IP при отказе ядра | **не сохраняется** (UE получает IP из пула живого ядра) | **сохраняется** (IP из подписки, общий пул) |
| Динамический IP при отказе | новый IP из чужого пула | новый IP (re-attach), но из того же пула |
| Риск коллизий IP | исключён (пулы непересекающиеся) | есть для динамики — нужен механизм координации |
| RTO при отказе ядра | re-attach, секунды | re-attach, секунды |
| Подходит для | динамических абонентов | статических IP, требования сохранить IP |

### 4.2. Вариант A — разделённые пулы (prefix-routing)

Ядрам назначаются **непересекающиеся пулы** абонентских IP: пул A → ядро A,
пул B → ядро B. DN маршрутизирует downlink по префиксу: пакеты с DST IP из пула A
идут на UPF-A, из пула B — на UPF-B. Каждый UPF получает только «свой»
downlink и обрабатывает его штатно — без пересылки.

При отказе ядра A абоненты пула A выполняют re-attach в ядро B и получают адреса
из пула B. DN начинает маршрутизировать их трафик на UPF-B. Сохранить старый IP
из пула A невозможно (он принадлежит отказавшему ядру).

Достоинства: нулевой межядерный трафик, отсутствие IPIP, никаких дополнительных
требований в UPF, нет риска коллизий IP.

### 4.3. Вариант B — общий пул (ECMP + IPIP miss-forward)

Оба ядра используют **общий пул** абонентских IP. DN ведёт ECMP на оба UPF.
Из-за этого часть downlink-пакетов абонента из ядра A попадает на UPF-B.
UPF-B не находит сессию по DST IP и по miss-правилу пересылает пакет через IPIP
на UPF-A, который обрабатывает его штатно.

При отказе ядра A абоненты выполняют re-attach в ядро B. Поскольку пул общий,
**статически назначенные IP сохраняются** (IP из подписки действителен в обоих
ядрах). DN продолжает ECMP, теперь UPF-B находит сессии у себя — пересылка
прекращается.

**Риск коллизий для динамических IP:** два ядра могут одновременно выделить
одинаковый IP разным абонентам. Требуется координация: непересекающиеся
динамические субпулы внутри общего пула, либо централизованное выделение адресов.
Для статических IP (уникальны по подписке) риск отсутствует.

Достоинства: сохранение статических IP при отказе, единая конфигурация пула.
Недостатки: постоянный межядерный трафик (~50% DL), требуется поддержка в UPF,
риск коллизий динамики.

## 5. Потоки трафика

### 5.1. Uplink (UE → DN) — общий для обоих вариантов

gNB знает якорный UPF для каждой PDU-сессии (по N3 TEID, выданному SMF). Трафик
GTP-U с нужным TEID направляется **только** в UPF якорного ядра. UPF находит
сессию по TEID, декапсулирует GTP-U и маршрутизирует внутренний IP-пакет в DN.
Пересылка между UPF в uplink **не используется**.

### 5.2. Downlink — Вариант A

DN шлёт IP-пакет с DST IP = IP абонента. По префиксу пакеты пулa A идут на
UPF-A, пулa B — на UPF-B. UPF находит сессию по DST IP и инкапсулирует в GTP-U
(N3) для отправки в gNB. Штатный путь, без пересылки.

### 5.3. Downlink — Вариант B

**Локальный (сессия «своя»).** DN шлёт пакет на UPF, где сессия создана.
UPF находит её по DST IP, инкапсулирует в GTP-U (N3), отправляет в gNB.

**Через пира (сессия «чужая»).** Из-за ECMP пакет абонента из ядра A попадает на
UPF-B. UPF-B не находит сессию по DST IP. По miss-правилу инкапсулирует
**исходный IP-пакет** в IPIP и отправляет на UPF-A. UPF-A деинкапсулирует IPIP,
получает «чистый» IP-пакет и обрабатывает как обычный N6-трафик: находит сессию
по DST IP, инкапсулирует в GTP-U (N3), отправляет в gNB.

```
DN ──[DST IP = UE]──► UPF-B  (нет сессии)
                        │  IPIP-encap
                        ▼
                     UPF-A  (есть сессия)
                        │  N3 GTP-U
                        ▼
                       gNB ──► UE
```

## 6. Особенности механизма пересылки (Вариант B)

### 6.1. Идентификация сессии

- **Downlink (N6):** поиск сессии по DST IP.
- **Uplink (N3):** поиск сессии по N3 TEID. Пересылка по uplink не выполняется.

### 6.2. Miss-правило (catch-all)

Текущее поведение при отсутствии сессии — пакет передаётся ядру ОС. В Варианте B
это поведение заменяется:

1. Пакет пришёл **со стороны N6** (внешняя сеть DN), сессия **не найдена**,
   DST IP **не является локальным** (см. 6.5) и пакет **unicast** (см. 6.7):
   → **IPIP-инкапсуляция** и отправка на адрес пира UPF.
2. Пакет пришёл **со стороны IPIP-интерфейса** (уже переслан пиром), сессия
   **всё ещё не найдена**:
   → **`DROP`** (защита от циклов, см. 6.4).

### 6.3. IPIP-инкапсуляция / деинкапсуляция

- **Инкапсуляция (на UPF, не найдена сессия):** поверх исходного IP-пакета
  добавляется внешний IPv4-заголовок:
  - `src` = локальный адрес UPF на IPIP-линке;
  - `dst` = адрес пира UPF на IPIP-линке;
  - `protocol` = 4 (IPIP).
- **Деинкапсуляция (на пире):** входящий пакет с `protocol == 4` на
  IPIP-интерфейсе разбирается, внешний IP-заголовок снимается, внутренний
  IP-пакет передаётся в обычный downlink-обработчик
  (`handle_n6_packet_ipv4` / `handle_n6_packet_ipv6`).

IPIP выбран вместо GTP-U (N9) сознательно: после декапсуляции пакет обрабатывается
стандартным N6-путём по DST IP, **без необходимости создавать и синхронизировать
дополнительные PDR с ключом TEID** между ядрами.

### 6.4. Защита от циклов (anti-loop)

Риск: если IP не находит ни в одном UPF (расхождение конфигураций, ошибочно
маршрутизированный пакет), наивная логика «miss → переслать» приведёт к
бесконечному ping-pong A↔B.

**Защита:** источник пакета определяет действие. Пакет, прибывший **уже через
IPIP-интерфейс** (т.е. пересланный), при повторном miss-совпадении **выбрасывается
(`DROP`)**, а не пересылается обратно. Максимум одна итерация пересылки на
пакет.

### 6.5. Исключение локальных адресов

Miss-правило применяется **только** к трафику, адресованному абонентам. Пакеты,
адресованные самим UPF, не должны уходить к пиру. Исключаются:

- локальные N3/N9-адреса UPF;
- адреса управления (API, PFCP, Prometheus);
- адреса BGP/маршрутизации, если используются.

Проверка «не локальный адрес» выполняется **до** принятия решения об
IPIP-пересылке.

### 6.6. MTU и PMTU

- **MTU:** IPIP добавляет **20 байт** внешнего IPv4-заголовка. MTU межядерного
  канала должен быть ≥ MTU N6 + 20.
- **Ловушка PMTU:** при превышении MTU промежуточный маршрутизатор генерирует
  ICMP Frag-Needed, но он приходит на UPF (источник внешнего IPIP-заголовка),
  а не на исходного отправителя в DN. Ретрансля PMTU в DN не происходит
  автоматически, и легитимные полноразмерные пакеты могут отбрасываться.
  **Рекомендация:** поднять MTU межядерного канала ≥ N6 MTU + 20, чтобы
  избежать фрагментации и зависимости от PMTU.

### 6.7. Только unicast

В miss-путь попадают также broadcast/multicast и потенциально вредоносный
сканирующий трафик. Для предотвращения рефлексии/амплификации IPIP-пересылка
выполняется **только для unicast-пакетов**. Broadcast/multicast на miss-пути
отбрасываются.

### 6.8. Обработка устаревших/IDLE-сессий

**Сценарий:** абонент выполнил re-attach в ядро B, но в ядре A осталась
устаревшая IDLE-сессия. SMF ядра A сохраняет downlink PDR (поиск по DST IP
находит сессию), но переводит FAR в режим NOCP (без FORW) — пересылка
запрещена, ожидается paging.

**Поведение без фикса:** DL-пакет, хешированный на UPF-A (stale-сессия),
находит сессию, но FAR=NOCP → `XDP_DROP`. Пакет теряется, не пересылается
пиру. При этом срабатывает NOCP-триггер — SMF ядра A получает
DownlinkNotificationReport и пытается page UE (бесполезно, UE в ядре B).
Результат: ~50% DL-loss для affected-абонента + бессмысленный paging.

**Поведение с фиксом:** если сессия найдена, но FAR не содержит FORW,
применяется `try_rebalance` — пакет пересылается пиру (UPF-B), где активная
сессия доставляет его абоненту. NOCP-триггер сохранён до rebalance, поэтому
SMF ядра A получает нотификацию как сигнал к очистке устаревшей сессии.
Anti-loop: redirected-пакет с non-FORW FAR → `XDP_DROP` (не уходит обратно).

---

## 7. Плоскость данных (Вариант A)

Изменений не требуется. UPF работает штатно: downlink ищется по DST IP в
`pdr_map_downlink_ip4/6`, при отсутствии — `XDP_PASS` (ядро ОС). Поскольку DN
маршрутизирует по префиксу, «чужого» downlink не возникает. Uplink — штатно по
TEID.

## 8. Конфигурация

### 8.1. Общие требования

- **gNB:** два NG-контекста (к 5GC-стороне каждого ядра). Выбор ядра для UE —
  на этапе регистрации (AMF selection, TAC/планирование).
- **Uplink:** gNB направляет по N3 TEID в якорное ядро — настройки UPF не
  меняются.

### 8.2. Вариант A

- **Пулы IP:** непересекающиеся пулы для ядер A и B (напр. `10.60.0.0/25` → A,
  `10.60.0.128/25` → B). Назначаются через SMF/UDM каждого ядра.
- **DN-маршрутизация:** статические маршруты или BGP: префикс пула A → UPF-A,
  префикс пула B → UPF-B. ECMP не требуется.
- **UPF:** без изменений; стандартные поля `n3_address`, `n6` через
  `interface_name` и т.д.

### 8.3. Вариант B

Конфигурация UPF расширяется (по стилю существующих полей в
`cmd/config/config.go`, напр. `n9_address`, `n9_adv_address`):

| Поле | Назначение |
|---|---|
| `ipip_peer_address` | IP-адрес пира UPF для IPIP-туннеля (destination внешней инкапсуляции). |
| `ipip_local_address` | Локальный IP UPF на IPIP-связи (source внешней инкапсуляции). |
| `ipip_interface` | Идентификатор/имя интерфейса меж-ядерной связи (для anti-loop, 6.4). |

Реализация поддерживает несколько абонентских префиксов (несколько APN):
список `ip4_ue_prefixes` (CLI `--ip4prefs`, повторяемый флаг) хранится в eBPF
в виде LPM-trie (`ue_rebalance_lpm_map`), один глобальный адрес пира
(`rebalance_address`/`rebalance_local_address`) применяется ко всем префиксам.

Дополнительные требования к окружению:

- **ECMP у DN:** строго **per-flow (5-tuple)**. Per-packet хеширование недопустимо
  (изменение порядка пакетов). Допускается L3-only hash, если потоки UE
  достаточно распределены по DST IP, но L3/L4-хеш предпочтителен.
- **Отсутствие NAT/PAT на N6:** DN видит реальный IP абонента (DST IP = IP UE).
  Обязательное условие корректности miss-правила (поиск по DST IP).
- **Подсеть IPIP:** выделенная подсеть UPF-A ↔ UPF-B, изолированная от N3 и N6
  (не публикуется в DN).
- **Координация динамических IP:** непересекающиеся динамические субпулы внутри
  общего пула или централизованное выделение — во избежание коллизий.

Контрольная плоскость (PFCP/N4) остаётся в пределах якорного ядра — между ядрами
PDR/FAR/QER **не реплицируются**.

## 9. Сценарии отказов и их обработка

| # | Сценарий отказа | Вариант | Воздействие | Механизм восстановления | RTO |
|---|---|---|---|---|---|
| 1 | **Отказ UPF ядра A** (ядро живо, UPF down) | A | DL абонентов пула A теряется; uplink в «мёртвый» N3-туннель | gNB фиксирует отсутствие ответа N3 → re-attach UE в ядро Б, новый IP из пула Б | Секунды |
| 1 | **Отказ UPF ядра A** | B | DL абонентов A, хешированный на UPF-A, теряется; uplink в «мёртвый» N3 | Re-attach в ядро Б, **статический IP сохраняется** | Секунды |
| 2 | **Отказ всего ядра A** (AMF+SMF+UPF) | A/B | То же + потеря CP-контекста | Re-attach в ядро Б (5G AKA / EAP-AKA'); IP: A — из пула Б, B — сохраняется (статика) | Секунды |
| 3 | **Обрыв IPIP (1 из 2+ линков)** | B | Частичная деградация пропускной способности межядерного канала | ECMP/LACP перенаправляет на оставшийся линк | Миллисекунды |
| 4 | **Полный обрыв IPIP** | B | **Все** абоненты теряют ~50% DL (половина, хешированная на не-якорный UPF, не пересылается). Uplink не затронут | Восстановление линка; до этого TCP восстанавливается ретранссией, UDP страдает | Зависит от транспорта |
| 5 | **Обрыв DN-маршрута к UPF-A** | A | DL абонентов пула A полностью теряется | Восстановление маршрута; либо re-attach в Б (но IP из пула Б) | Секунды |
| 5 | **Обрыв DN-маршрута к UPF-A** | B | Весь DL перенаправляется на UPF-B → при чужих сессиях уходит через IPIP на UPF-A. **Деградация задержки**, сервис сохранён | Восстановление маршрута | Секунды |
| 6 | **Обрыв NG к одному ядру** | A/B | UE не могут регистрироваться в отказавшем ядре; существующие сессии этого ядра теряются | Re-attach через живое NG-подключение | Секунды |
| 7 | **Двойная сессия** (re-attach без cleanup старой IDLE) | B | DL на UPF со stale-сессией: FAR=NOCP → без фикса DROP (~50% loss + paging через старое ядро) | Rebalance при non-FORW FAR; NOCP-нотификация сохранена для cleanup | Мгновенно (rebalance) |

> Примечание: во всех сценариях с отказом ядра восстановление **не бесшовное** —
> абонент проходит повторную регистрацию. Разница между вариантами — в
> сохранении IP: Вариант A выдаёт новый IP из пула живого ядра, Вариант B
> сохраняет статический IP (общий пул).

## 10. Мониторинг

Рекомендуемые метрики (Prometheus, в стиле `docs/metrics.md`) — в основном для
Варианта B:

- `upf_ipip_forwarded_packets_total` — пакеты, пересланные пиру (miss на N6).
- `upf_ipip_received_packets_total` — пакеты, полученные по IPIP от пира.
- `upf_ipip_loop_dropped_total` — пакеты, отброшенные по anti-loop (miss на
  IPIP-интерфейсе).
- `upf_ipip_local_dropped_total` — пакеты, исключённые из пересылки как
  локальные/не-unicast.
- `upf_ipip_encap_errors_total` / `upf_ipip_decap_errors_total` — ошибки
  инкапсуляции/декапсуляции.

Интерпретация:

- Высокое `upf_ipip_forwarded_packets_total` относительно общего DL — индикатор
  дисбаланса ECMP или ошибки конфигурации (перекрывающиеся пулы, нарушение
  координации динамики).
- `upf_ipip_loop_dropped_total > 0` — признак рассинхронизации таблиц PDR между
  ядрами.

Для Варианта A специфические метрики не требуются — используются стандартные
счётчики UPF (`upf_*`).

## 11. Безопасность

- **Доверенный транспорт (Вариант B).** Канал IPIP рассматривается внутри
  доверенной среды передачи (выделенная линия/защищённый VLAN). **IPsec не
  требуется** в базовой схеме; при необходимости добавляется на уровне
  транспорта без изменения плоскости данных.
- **Анти-рефлексия.** Miss-путь пересылает только unicast; broadcast/multicast
  не пересылаются, что снижает риск отражательных атак.
- **Анти-цикл.** Ограничение на одну итерацию пересылки (6.4) исключает
  бесконечную циркуляцию пакетов.
- **Изоляция подсети IPIP.** Межядерный канал не публикуется в DN и не
  пересекается с N3/N6.
- **Вариант A** — IPIP отсутствует, дополнительные меры безопасности не требуются.

## 12. Ограничения и риски

1. **Нет бесшовного failover ядра (оба варианта).** Схема — резервирование *пути*
   downlink и горячий резерв ядра, а **не** репликация состояния сессий. При
   отказе якоря — re-attach с перерывом и повторной аутентификацией.
2. **Сохранение IP (различие вариантов).** Вариант A не сохраняет IP при отказе
   (новый из чужого пула). Вариант B сохраняет статические IP, но требует
   координации динамических пулов во избежание коллизий.
3. **Стоимость Варианта B в нормальном режиме.** До ~50% downlink постоянно
   проходит через межядерный канал; канал и оба UPF должны быть рассчитаны
   на этот трафик.
4. **SPOF при одиночном IPIP-линке (Вариант B).** Требуется 2+ независимых линка
   (ECMP/LACP); иначе полный обрыв связи = потеря ~50% DL для всех абонентов.
5. **Зависимость от ECMP у DN (Вариант B).** Корректность требует per-flow
   хеширования и отсутствия NAT на N6.
6. **PMTU-ловушка (Вариант B).** ICMP Frag-Needed приходит на UPF, а не на
   отправителя в DN — рекомендуется поднять MTU канала.
7. **Отсутствие 3GPP-стандарта** для постоянного меж-UPF «miss-forwarding» —
   решение кастомное, требует поддержки в eBPF-двигателе UPF (Вариант B).

## 13. Рекомендация по выбору варианта

- **Динамические абоненты без требования сохранить IP** → **Вариант A**.
  Проще, надёжнее, нулевой межядерный трафик, без изменений в UPF.
- **Статически назначенные IP / требование сохранить IP при отказе ядра** →
  **Вариант B**. Общий пул, ECMP + IPIP miss-forward.
- **Гибрид:** динамические абоненты — по Варианту A (разделённые субпулы,
  prefix-routing), статические — по Варианту B (общий статический диапазон,
  ECMP + IPIP). Требует, чтобы DN комбинировал prefix-routing для динамики и
  ECMP для статики; реализуемо при поддержке со стороны маршрутизации DN.
